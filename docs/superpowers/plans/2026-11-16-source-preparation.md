# Source connection preparation implementation plan

> **For agentic workers:** Execute inline with executing-plans; require one independent whole-change review before merge.

**Goal:** Move fixed source statement description/preparation into normal serving initialization without loading search results or increasing request deadlines.

**Architecture:** Install a migration-gated pgx PrepareConn hook on the serving pool. After schema validation activate it and acquire/ping before listening. Prepare six existing catalogue/vocabulary SQL shapes without parameters; pgx reuses descriptions on subsequent acquisitions and prepares replacement connections independently. Keep health configuration separate and preserve existing connection-hook precedence.

**Tech Stack:** Go 1.26.11, pinned pgx 5.10.0, PostgreSQL 18.7.

**Spec:** User-authorized source-read optimization; source-read-tails plan. Normal server startup includes its existing schema-version query in both comparison variants.

## Global constraints

Source/target max pools 8/4, request and SQL deadlines unchanged. The added preparation stage is bounded by the caller context and five seconds, whichever expires first. No executing searches, no actual query values, no data cache, no record/index preloading, no schema or index change. Original frozen acceptance remains required. v14 stays hidden until publication proof passes.

## Review focus

- First desktop launch must migrate an empty archive while preparation is inactive.
- Activation and preparation complete before listening; initialization errors fail closed.
- Each replacement connection prepares; reused descriptions avoid repeat server parsing.
- Existing PrepareConn or legacy BeforeAcquire hooks retain their behavior/precedence.
- Health-pool configuration is copied before adding the source-only hook.
- Cancellation discards failed connections and returns no poisoned connection; a later acquisition recovers.
- Coverage follows the SQL generated by actual catalogue/vocabulary consumers, and preparation executes zero source searches.

## Decision and diagnostic limitations

Direct ParadeDB postcode routing failed all eight prototype requests; source block reordering also failed to improve the cold tail. A simpler catalogue query did not reduce preparation cost. Those prototypes were not adopted. A prepare tracer found hundreds of milliseconds in cold Parse/Describe metadata work. Fixed, request-independent preparation is a startup responsibility; account for that cost explicitly rather than claim less total work.

The faithful source-cold ABBA comparison includes the existing schema-version check in both variants. First-request baseline times were 1,625/1,509 ms; proposed times 1,278/1,386 ms. Pool initialization rose from 593/582 ms to 794/712 ms. All eight responses completed and exact full bodies/cursors matched, with zero search reads during initialization. The earlier prototype omitted the server's schema check and is retained separately; use the faithful comparison for conclusions. Both are diagnostic, not full acceptance or capacity proof.
