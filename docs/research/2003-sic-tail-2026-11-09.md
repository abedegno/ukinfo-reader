## Rank first, then choose one change

Offline analysis of the retained street-only C4 run found 35 structural shapes
among 127 cases. Fourteen cases had at least one observation above 1 s; thirteen
of those used business SIC filters. The leading shapes were SIC prefix+town in
catalogue order, SIC prefix in name order, and exact SIC in name order. Ranking
used max of two observations per case, not a statistically robust case percentile.
Selection was deterministic: the slowest case from each of the top three shapes.
No query was executed while ranking; query strings/ordinals remained on NAS.

Three read-only generic EXPLAIN ANALYZE calls used the existing API role against
the retained full 2003 index, with 4 s deadlines. All used TopKScanExecState and
returned 51 candidates; times 1,236/634/366 ms. The serialized queries showed
parameterized expressions. This motivated one policy trial: keep all original
scalar/nonempty/kind/address checks, add a bound exact SIC term or escaped regex
prefix, and preserve every ordering/seek/limit rule. No data or index rebuild.

## Follow the actual query, not only its serialized appearance

One actual parameterized SQL capture per selected shape confirmed that all three
application statements emitted the proposed term/regex condition. A diagnostic
guard initially stopped on equivalent quoted/unquoted lowercase table names.
It retained the first capture before any paired plans ran; a guarded continuation
normalized only those fixed identifiers, adopted that capture and collected the
two remaining ones. No completed request/plan or HTTP cohort was replayed.

Twelve generic EXPLAIN ANALYZE observations then followed fixed scalar/policy/
policy/scalar order, all successful under the same 4 s deadline:

| Shape | Scalar A1 | Policy B1 | Policy B2 | Scalar A2 |
| --- | ---: | ---: | ---: | ---: |
| SIC prefix + town | 839 ms | 475 ms | 461 ms | 366 ms |
| SIC prefix, name order | 593 ms | 484 ms | 463 ms | 610 ms |
| Exact SIC, name order | 321 ms | 268 ms | 271 ms | 277 ms |

All retained Top-K, four segments, 51 heap fetches and no temp blocks. Prefix+
town's first scalar observed shared reads; its warm scalar was faster than the
policy. Prefix/name showed a modest directional gain. Exact SIC used the same
819 shared-buffer accesses throughout. These small observations do not justify
blanket production adoption, especially with the full HTTP gate still false.
Three custom-plan EXPLAIN-only calls showed static representations, but custom
execution was not measured and no application/global planning mode was changed.

An important interpretation correction: pg_search 0.26.3 resolves
PostgresExpression query-builder nodes before scanning. Their presence in a
serialized generic plan does not prove ineffective per-row filtering or a missing
index constraint. My earlier interpretation was too strong. [Official versioned
implementation](https://github.com/paradedb/paradedb/blob/v0.26.3/pg_search/src/postgres/customscan/solve_expr.rs).
This does not prove a custom plan would be faster; it was not timed.
