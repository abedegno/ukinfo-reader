UK-Info search storage spike

17 October 2026 · Real-data sample · Go, PostgreSQL, SQLite and Parquet

Recommendation: start with Go + PostgreSQL for both hosted and embedded desktop use, following Muesli's existing architecture. Both SQL engines performed well in the tested read workload.

Scope: two million sampled occurrences and 210 repeated HTTP query cases. The short warm-cache tests establish implementation feasibility. Full-dataset capacity, sustained VPS performance and native desktop packaging remain open.

Total: 189,064,266 occurrences, with 2.34 GiB of required original query files. These occurrences include separate electoral, telephone and business records; they are not distinct people.

The sample contains two million distinct source occurrence IDs from the four 2005 base/update residential/business streams. A fixed random seed selects byte-region clusters; overlap is deduplicated. Fourteen flattened columns were materialized for the experiment:

id, source_id, entry_type, surname, first_name, organisation, postcode, sector, houseno, building, street, town, county, phone

Names and search keys were case-folded, visible postcodes normalized, and partial postcode precision respected when deriving sectors. A production import must retain original display values and the complete source-warning/provenance payload.

Query cases cover exact person, surname, postcode, postcode+surname, sector+surname, exact organisation and surname prefix, mixing common and rare values. Results are ordered and limited to 50 rows. The SQL diagnostic also includes record-ID and missing-person cases.

All database-layer selected fields matched the reference. Both Go HTTP services passed 420 field-by-field case checks; timed HTTP responses were checked against those reference body hashes.

Parquet used Zstandard compression and 16,384-row groups. Requests were routed to the most favourable full sorted copy; the total includes all four copies. A single sorted copy should not be assumed to serve every access pattern equally well.

Native-host preparation took approximately 8.6 seconds for SQLite, 12.6 seconds for PostgreSQL, and 7.5 seconds for all four Parquet layouts. SQLite and Parquet preparation used the uncapped native host. PostgreSQL preparation ran inside the capped database container; the import client ran on the native host. These are different preparation environments.

5. Parquet and analytical work

The SQL diagnostic grouped all two million rows by county. PostgreSQL and SQLite had no county index in this prototype:

Engine / layoutMedian aggregation time
sqlite440.63 ms
postgres191.50 ms
parquet8.50 ms

DuckDB over Parquet was effective for this columnar aggregate. Direct Parquet lookup queries incurred more per-query work than indexed SQL in the diagnostic, but that test used a different client path from the Go HTTP comparison. A Go/DuckDB HTTP endpoint, remote object storage and cold-cache Parquet searches were not tested.

The Parquet specification describes page skipping and sorted-column access while explicitly excluding general secondary indexes from the page-index design. DuckDB’s guidance explains the trade-offs around row groups and layout. Parquet is useful for export and analysis; adopting it does not remove the need to design the serving access paths.

6. Bounded fuzzy-name candidate generation

The sample has 43,056 distinct nonempty surnames. Their PostgreSQL GiST trigram index occupies 2.9 MiB. Ninety candidate-generation queries used an index scan, with median 3.54 ms and p95 4.41 ms, including a host-to-Docker connection hop.

This checks finding up to twenty similar dictionary names. It excludes retrieving/ranking their matching occurrences. Matching the small name dictionary before consulting occurrence indexes is a useful schema candidate to test at full scale. Exact short names and initials need their own exact/prefix handling. See PostgreSQL trigram documentation.

7. PostgreSQL data-pack import

A custom-format pg_dump produced a 50.9 MiB pack in 3.61 seconds. Restoring into a fresh database took 6.09 seconds. All two million rows were restored, and aggregate checks over every row/column matched.

This is a practical bootstrap mechanism for an app-managed local PostgreSQL instance. The test used the same PostgreSQL version and architecture. For cross-platform distribution, use a logical pack and initialize a local cluster; PostgreSQL documents logical-dump portability and physical-backup version constraints. Native macOS/Windows startup and upgrades still need explicit tests.

8. Recommendation and next decision gate

  • Serving: Go + PostgreSQL in both modes, with one schema, query implementation and migration path. Muesli provides relevant prior art for the Electron/Go/local-PostgreSQL process lifecycle.
  • Import: retain the validated Python decoder as the importer/reference. The Go service can query prepared data without running the Python decoder for each request. The spike gives no evidence requiring a Rust rewrite.
  • Schema: preserve source occurrences, edition identity, display text and warnings. Benchmark a lean search projection and separate detailed addresses/provenance. Test dictionary-based fuzzy candidate generation and partial indexes before indexing every text field on every occurrence.
  • Distribution: a compressed PostgreSQL logical pack is already viable in this prototype. Parquet can be added for analytical/export requirements without making it a required serving layer.
  • Desktop: assess the existing Electron packaging pattern. Verify first-launch restore, offline reopen, user-selected data directory/relocation, crash cleanup, supported OS/architecture bundles and PostgreSQL major-version upgrades.

A naive linear size check for this flat PostgreSQL prototype is approximately 59.1 GiB for all four editions. That is not a production sizing prediction: normalization, full provenance, additional fields and indexes will change it. It does show why the earlier small-VPS price estimate was premature.

Next gate: build one complete edition with the intended production schema, then run sustained mixed-query tests on the proposed VPS using cold and warm caches, a broad unseen-key distribution, keyset pagination, candidate expansion, cross-edition filters and concurrent exports. Choose the hosting plan from those results.

9. Limits and reproducibility

  • This is a short engineering spike, not a production capacity certification.
  • Two million unique occurrences from the 2005 edition: about 3.9% of that edition and 1.1% of all currently supported occurrences.
  • The sample uses seeded byte-region clusters and excludes duplicate occurrence IDs. It is not an unbiased population sample.
  • The prototype has fourteen flattened columns. It omits the full production provenance/warning payload and several source fields; production storage must be measured again.
  • HTTP tests repeatedly exercised 210 common/rare exact and prefix query cases, limited to 50 rows, with warm caches. Broad unseen-key, cold-cache, deep-pagination and full multi-edition behaviour were not measured.
  • Each closed-loop level lasted five seconds; scheduled-arrival tests sent 500 requests at 100 requests/second. These timings are too short to establish long-running capacity or operational stability.
  • HTTP service and load generator used separate containers. Each backend was limited to two CPU quotas and 1 GiB memory; this is a Docker Desktop ARM64 test, not a target-VPS hardware test.
  • Both Go services used eight database connections and a 64-request admission cap. Tests reached 32 simultaneous callers; overload beyond that cap was not exercised.
  • The load generator validates response bytes against field-checked reference hashes. Its HTTP measurements include transport, body validation and pool waits, while excluding client JSON parsing.
  • DuckDB/Parquet was tested through its Python SQL interface, rather than the Go HTTP endpoint. Its timings cannot be directly ranked against Go HTTP timings.
  • The raw Python multithreaded SQLite measurements differed substantially from the common-Go HTTP measurements. Their cause was not isolated; use the Go HTTP test for application comparisons.
  • Parquet had four full Zstandard-compressed sorted copies, with routing to the favourable copy for each query. The storage total includes all four.
  • The surname trigram experiment measures candidate-name generation only. Fetching/ranking matching occurrences and full fuzzy-address queries were not benchmarked.
  • SQLite and Parquet preparation ran on the uncapped native host. PostgreSQL preparation and data-pack dump/restore ran in the capped database container, with a native-host preparation client.
  • Data-pack restore was tested on the same PostgreSQL version/architecture. Native desktop startup, Windows distribution, relocation and major-version upgrade paths remain untested.
  • Rust was not benchmarked; this spike provides no evidence that a Rust rewrite would improve the service.
