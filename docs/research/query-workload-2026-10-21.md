# Full-catalogue query review — 21 October 2026

## What this review found

The earlier incident fixes did not establish reliable performance across the
search feature set. Broader tests found three separate costs: unnecessary ordered
candidate expansion, expensive classification/address intersections, and fetching
compressed record blocks. A small warm workload performs well while previously
unread records and broad intersections can still exceed the API deadlines.

The implemented changes are:

- Expand name/first-name pairs in lexical order until the requested page and
  lookahead are full, instead of expanding all 128 pairs before sorting/limiting.
  Batch up to four sparse pairs using exact occurrence counts; keep dense pairs
  scalar to avoid speculative work. A 100-item sparse fixture page needs 27
  ordered queries instead of 102.
  Apply this to postcode-based name sorting and listing grouping too.
- Resolve an anchored business record's classification by source ID before testing
  industry/SIC. Fencing the complete EXISTS did not prevent the planner from
  choosing a national industry-range index for each record.
- Skip a second identical overflowing source probe. Retain the second probe when
  a complete address intersection changes its predicate.
- Resolve grouped representatives through exact per-edition group-key probes,
  stopping at the lowest ordinal and skipping later editions once resolved. This
  retains the original minimum `(dataset_id,id)` representative and complete
  cross-edition counts while avoiding a costly all-edition DISTINCT lookup.
- Add an optional ID-to-label dictionary covering index, alongside the existing
  label-to-ID covering index, with compatible-shape and validity guards.
- Measure vocabulary, probes, address lookups, candidates, ordered candidates,
  group members and record loading separately, using fixed OTel names and metric
  labels. Add a Terraform-managed stage-latency chart.

The request and serving-role SQL deadlines are unchanged.

## Method and limits

The private NAS API used the production read-only role and five full editions:
248,951,107 visible entries. API limits were one CPU, 512 MiB and eight database
connections; PostgreSQL had two CPUs, 6 GiB and 1 GiB shared buffers. The workload
client had half a CPU and 256 MiB. Tests ran directly on the isolated database
network, without public ports, Cloudflare or public per-client quotas. Source
verification/import maintenance shared the HDD array throughout.

There was no database copy or cache flush. First observations precede warming by
each runner, but earlier work and the OS/PostgreSQL caches affect them. Runs were
sequential, with different cache histories and changing maintenance activity.
Before/after timings are observations, not a controlled causal speedup estimate.
No whole-catalogue or Internet capacity claim follows from a short repeated test.

Reference cases came from the unchanged hosted-2026-10-21.3 API against independently
retained original Mac catalogues. The original 815-case set contained one input
rejected on both systems; 814 usable references remained. A further 62 edge
references were captured from 63 attempts. Expected hashes were not generated by
the optimized NAS implementation. Only opaque cursor bytes were replaced by
next-page availability; all other response content/order remained significant.
Complete cursor traversal is tested separately in CI.

Queries, source identities, expected hashes and response records remain private.
The [measurement artifact](query-workload-2026-10-21-results.json) contains aggregate measurements only. Failed attempts remain
in latency percentiles.

## Full-catalogue observations before final dictionary validation

The original 814-case reference run produced 788 exact matching successes and 26
HTTP 503 responses, with no response mismatches. Median latency was 281 ms, p95
1,673 ms, and the run lasted 395 seconds. It includes ordinary names, given-name
variants, postcodes and businesses from four independently retained editions.

The broader 83-case workload ran twice per version, exercising all five editions
and all-edition queries, address combinations, business classifications, grouping,
ordering and NDJSON exports:

| Family | Attempts | Original server failures | Lazy-pair + ID-first classification failures |
| --- | ---: | ---: | ---: |
| Address | 62 | 13 | 8 |
| Grouped | 18 | 18 | 10 |
| Ordered | 24 | 4 | 2 |
| Postcode, including classifications | 46 | 8 | 3 |
| Export | 16 | 0 | 0 |
| **Total** | **166** | **43** | **23** |

Median latency changed from 250 to 58 ms; p95 from 4,309 to 4,075 ms. These remaining
failures are substantial. Success without an independent hash in this exploratory
workload is marked unverified. An early runner incorrectly treated successful
NDJSON exports as invalid JSON; the corrected runner handles NDJSON and the table
counts actual HTTP failures, not those validation errors.

The same fourteen difficult searches were profiled through the real API handler,
with its normal deadlines. Failed requests fell from fourteen to four on the later
observation. Remaining slow stages included an industry/postcode intersection,
broad surname/address intersections and street ordering. Three ordinary postcode
requests spent 371–1,050 ms loading records despite fast candidate selection; they
had previously spent approximately 1.8–1.9 seconds in that stage and timed out.
Repeated/cache effects matter here as well. Sanitized EXPLAIN plans are estimates,
not measured disk reads or row counts.

## Adverse post-publication observation

A final repeat of the same 166-request feature workload, after the corrected 2003
edition published and while its logical backup was running, produced **77 HTTP
503s**: address 25/62, grouped 18/18, ordered 9/24, postcode/classification 24/46,
and export 1/16. Median latency was 2,017 ms and p95 5,001 ms. The dictionary index
was valid. This worse result is retained in the artifact; the earlier 43-to-23
observation must not be presented as a settled production reliability improvement.
The changed edition generation relative to the earlier runs, storage/cache state
and backup activity confound
comparison between these runs. They do demonstrate insufficient reliability under
maintenance load.

The new source/research partitions had approximately 94.5% and 92.6% all-visible
pages. The publication procedure vacuumed source entries and the dictionary, but
needed an explicit late step for research projections after old snapshots released.
`deploy/production/prepare-search-catalogue.sql` now codifies bounded ordinary
VACUUM/ANALYZE for the edition and shared lookups; the homelab publication procedure
runs it before future swaps. Source rows and serving deadlines are unchanged.

## Final independent-reference check

After the reciprocal dictionary index validated, all 876 independently hashed
cases were attempted within the budget. There were **834 exact matching successes,
42 HTTP 503s, and zero response mismatches**. Median latency was 267 ms, p95
2,001 ms, and the run took 477 seconds. Of the original 814 cases, 788 succeeded
and 26 timed out, the same totals as the original run; only six failures occurred
on the same case numbers in both runs. The additional 62 edge references had 46
successes and 16 failures. Cache history and ongoing finalization make comparisons
between these observation times unsuitable as a causal speedup estimate.

This is not a passing reliability result. The query changes reduce specific work
and improve the feature probes, while first-observation record access and broad
intersections still need attention. No reference hash was rebased to hide a failure.

## Paired regression check and representative fix

The first balanced, sequential baseline/candidate comparison on the same published
catalogue completed 83 pairs: 65 identical successful responses, eleven failures
on both APIs, one candidate-only success and six baseline-only successes. The
candidate therefore had seventeen failures against twelve on the baseline, with
zero content mismatches. Deployment was held. Four extra failures were grouped
postcode searches, despite fresh diagnostic runs succeeding.

A forced-generic diagnostic located expensive representative retrieval: the old
all-edition DISTINCT lookup took 719–1,264 ms in the four grouped cases. The new
per-edition exact-key probes took a few milliseconds in the follow-up diagnostic;
all six selected cases completed successfully. These observations still have
cache/background-load differences. The deterministic CI gate checks the actual
query under both planning modes: three probes over 50,000 invented keys used ten
shared buffers and zero heap fetches in each mode. Complete ordinary/grouped
pagination and earliest-edition source identity also pass.

## Final two-round paired result

Both APIs were freshly started with identical production limits on the same fixed
published catalogue. All 83 cases ran twice, with each API going first once per
case: **166 pairs / 332 requests**, no budget exhaustion. There were 152 identical
successful pairs, seven failures on both APIs, four candidate-only successes and
three baseline-only successes. No successful response content differed.

The baseline had eleven errors; the final candidate had ten. Median latency was
21 versus 27 ms, and p95 was approximately four seconds on both. Grouped searches
improved from four errors in eighteen attempts to one in eighteen, with median
320 versus 290 ms. The three candidate-only failures occurred when the candidate
went first in round one; all three matched successfully on both APIs in round
two. This suggests first-observation/cache sensitivity, without establishing a
causal explanation for each failure.

The final candidate therefore avoids the earlier persistent grouped-lookup
regression and preserves successful content, but **does not establish reliable
low latency for arbitrary cold searches**. Shared broad address/classification
and ordered-query failures remain. These outcomes, including candidate-only
misses, are retained rather than replaced with a warm-only passing report.

## Controlled repeated-workload capacity

A systematic subset used 48 evenly spaced original references plus 16 evenly
spaced edge references, selected without inspecting latency. The 64-case mix
included names, postcodes, businesses, addresses, grouped and ordered results.
It was measured before final dictionary-index validation.

| Concurrent clients | Completed requests | Requests/s | p95 ms | Errors or mismatches |
| ---: | ---: | ---: | ---: | ---: |
| 1 | 640 | 61 | 43 | 0 |
| 2 | 1,139 | 112 | 51 | 0 |
| 4 | 1,327 | 129 | 99 | 0 |
| 8 | 1,346 | 129 | 217 | 0 |

Each stage ran for ten seconds plus in-flight completion. All 4,452 responses
matched their independent references. Scheduled arrivals at two requests/second
completed all sixty requests, with p95 50 ms, zero errors/mismatches, no drops and
no budget skips. There was **one initial grouped-search timeout** before these
repeated stages, so the overall 4,576-request run correctly failed. Its initial
64 observations took 23 seconds, median 132 ms and p95 970 ms.

An earlier capacity attempt exhausted its 2,000-request budget before completing
all stages. It was retained as incomplete; these figures come from the corrected
10,000-request budget and do not splice successful stages from different runs.

This demonstrates cached repeated-query capacity. It does not establish 129
requests/second for arbitrary searches over 249 million entries. HDD record access,
cache misses and broad intersections remain the practical risks.

## Regression gates

- Complete ordinary/grouped paging over 360 invented name pairs, with unused
  dictionary terms interleaved, for both name and postcode anchors.
- A one-item sparse page expands only its two needed pairs in one batch. A dense
  first pair does not expand neighbouring pairs. Sparse full-page query work and
  the submitted-pair counter are checked as hard gates.
- Actual API business predicates over 50,000 invented projections: exact IDs/order,
  forced custom/generic plans, covered ID-first research access, classification
  filters outside the ID lookup, zero fixture heap fetches, fewer than 800 shared
  buffers. The previous predicate is rejected by this gate in an isolated source
  copy; the optimized predicate passes.
- Existing covering-index matrix, optional-index shape guards, selective/broad
  address paths, boundary probes, row cleanup, and full server race tests.
- HTTP runner tests for retained failures, digest mismatches, budgets, redirects,
  NDJSON and cursor-neutral comparisons; Collector tests for privacy and histogram
  conversion.

## Next engineering priorities

1. Keep the full reference and feature workloads as hosted-release checks, alongside
   smaller deterministic CI gates. The reciprocal dictionary index validated
   successfully after verification released its snapshots; it occupies 338 MiB.
2. Replace broad address-posting expansion with a measured hosted search projection
   joining source keys, location ID, listing-group key and business classifications
   once during import. First compare bounded source iteration through the existing
   reverse address arrays against that wider projection. Keep the compact portable catalogue as the source of truth.
   Prototype on a complete edition and compare exact identities, pagination, build
   time, disk use and first-observation latency before selecting indexes.
3. Measure record-block read amplification independently from candidate SQL. Compare
   the current compressed blocks on HDD with SSD placement or a hosted record
   serving projection. Additional candidate indexes cannot eliminate record reads.
4. Repeat the workload when import/verification maintenance is idle, and use a much
   larger rotating workload for sustained capacity. Record failures and storage
   waits alongside throughput; avoid tuning only for hot keys.

Increasing global deadlines, changing database language, or adding more connection
pool slots is not supported as a remedy by these measurements.
