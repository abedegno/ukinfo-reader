# UK-Info 2003 SE — DPCS0104DVD

This exact source is supported for residential, telephone and business search/export.
The installer identifies it as **UK-Info 2003 SE**; `CDID.TXT` contains
`DPCS0104DVD`. The supplied image is `DPCS0104DVD.ISO`, 4,687,949,824 bytes.
[Disc fingerprints](../validation/se2003-dpcs0104-media.json) establish the copy;
no Internet Archive copy has been independently verified. A disc identifier or
product year does not establish the records' electoral-roll reference date.

The reader uses a distinct `modern2003` dispatch, reusing shared binary primitives
only where verified. Treating the files as the 2004/2005 format misreads record
boundaries, house numbers and addresses.

## Extract and identify

The desktop wizard accepts the completed ISO once built from this source revision.
Its source profile requires these files, with exact sizes and hashes recorded in
[the registry](../../src/ukinfo_reader/editions.py) and
[the validation report](../validation/se2003-dpcs0104.json):

- Residential: `uk.dat`, `ukspos.idx`, `d2.dat`, `d3.dat`, `d4.dat`.
- Addresses: `d1.dat`, `d5.dat`, `d6.dat`, `d6pa.dat`, `d7.dat`, `d8.dat`.
- Businesses: `dbbus.dat`, `dd.dat`, `dbsic.dat`.

Large stream/string files are beside the installer at the ISO root; other tables
are in its InstallShield cabinets. The bounded media preparer extracts only profile
files, verifies all fourteen SHA-256 fingerprints and removes temporary cabinets.
It never runs the installer or original binaries.

For a source checkout with the cabinet helper built (see
[desktop builds](../desktop-releases.md#native-local-build)):

```sh
python -m pip install -e '.[media]'
python - <<'PY'
from ukinfo_reader.media import prepare
prepare('DPCS0104DVD.ISO', 'private/2003-reader')
PY
ukinfo-read --data private/2003-reader --identify
ukinfo-read --data private/2003-reader --surname Example --limit 20
ukinfo-read --data private/2003-reader --entry-type business --limit 20
ukinfo-validate --data private/2003-reader --output private/2003-validation.json
```

Keep source files, returned directory records and private queries outside Git.
Source extraction uses about 549 MiB; catalogue imports require substantially more
space. Stream imports as described in [the search application guide](../search-app.md)
instead of writing a complete intermediate JSONL export.

## Physical records

The source uses 1 KiB c-tree index pages with separate little-endian record pointers
and the same verified prefix/fill compression primitives as later releases.
All 846,040 surname-range keys were checked against residential record boundaries.

Residential records retain the later layout's name count, kind, name/postcode
references and optional building, subbuilding and telephone fields. Differences:

- The name dictionary mask is `0x1fffff`.
- Bit `0x80` in the postcode flag byte extends the house ID to seventeen bits.
  It does **not** add a trailing postcode-precision byte.
- The building reference is 24 bits; postcode flag `0x40` does not extend it.
  Raw postcode flags remain available as `postcode_flags`.
- Source kinds 0, 3, 4 and 5 supply the same distinct electoral/telephone occurrence
  model. Combined records retain both components. No update/deletion stream is
  present in this particular release.

Businesses use `dbbus.dat`, kind 0, one-based word offsets in `dd.dat`, and the
source's SIC dictionary. Optional field names and ordering were checked against
its original constructor: LOB, USIC, HOUSE, FLAT, TEL, EXC, FAX EXC and FAX TEL.
The business control byte does not add a precision byte or extend the building
reference. Telephone/fax formatting uses the verified older numeric convention.

## Postcode and address joins

Unlike `d6new.dat`, `d6.dat` does not begin with a complete postcode string.
Its eighteen-byte records contain:

| Offset | Bytes | Field |
| --- | ---: | --- |
| 0 | 3 | One-based row ID in `d6pa.dat` |
| 3 | 2 | Postcode suffix characters |
| 5 | 3 | Source `p_x` raw code |
| 8 | 3 | Source `p_y` raw code |
| 11 | 3 | Byte offset into the street strings in `d7.dat` |
| 14 | 4 | Source index-position field; unused by the joined reader |

The fifteen-byte prefix rows supply five bytes of postcode prefix at offset 0
and a two-byte locality ID at offset 9. Prefix plus suffix reconstructs the stored
postcode. A space is added only for a syntactically full postcode; partial source
values retain their actual precision and receive `partial_postcode_source`.
The prefix table's other exchange/index fields are not used to invent address data.

All 1,720,480 postcode rows were checked against the 227,034 prefix rows. Locality
ID `0xffff` is retained and flagged as `missing_source_locality`, with no invented
place text. All 27,958 locality text/type/parent records are byte-identical to the
corresponding fields of the independently validated 2004 table; the existing
locality → post town → county rules therefore apply to the same source relationships.

`postcode_x_raw` and `postcode_y_raw` retain the unsigned 24-bit source codes,
including sentinel values. Their coordinate system, scale and precision are not
asserted here, and they are not used for map positions.

## Complete validation and limitations

[Whole-source validation](../validation/se2003-dpcs0104.json) checks every physical
record, surname boundary, name/building/subbuilding reference and available address,
business word, SIC and telephone join.

| Source occurrences | Count |
| --- | ---: |
| Electoral | 44,959,860 |
| Residential telephone | 12,455,943 |
| Business | 2,471,038 |
| Total | **59,886,841** |

These are source occurrences, not deduplicated people, households or companies.
Five physical records before the first indexed surname range are excluded from
search/export. Seventeen emitted name references do not resolve in the supplied
name dictionary: text remains empty, the original code is retained and
`invalid_name_reference` is flagged. Twenty-five building references point inside
strings; the existing ambiguous-building policy preserves raw text without claiming
a reliable building name. The causes of these source defects are unknown.

The disc omits `lobdesc.dat`. Its 2,093,749 present line-of-business references
remain in `industry_reference_raw`; descriptions are null and carry
`industry_dictionary_missing`. Business names, addresses, telephone/fax and stored
SIC codes remain available. No replacement descriptions are guessed from another edition.

[Original-decoder comparisons](../validation/se2003-dpcs0104-reference-comparison.json)
execute recovered decoder routines locally with invented inputs: 1,280 residential
length/house cases, 65,536 business-length cases, 1,536 complete business-field cases
and 2,009 telephone-format cases, with no mismatches. Only allocation and array-runtime
functions are stubbed. This does not claim a comparison against the running Windows UI.
Original binaries, recovered code and emulator dependencies are not distributed.

### Spaces in postcode prefixes

The five-character prefix field can already contain the inward-code separator.
Classify postcode precision after removing whitespace, then render a full code
with one separator before the final three characters. Preserve the joined source
text in `postcode_raw`. Checking the spaced source against a compact-code pattern
incorrectly labelled valid full postcodes as partial and excluded them from normal
listing grouping. Genuine incomplete codes retain their partial warning.
