# UK-Info Disk v14 — supplied March 2008 release

This exact two-disc source supports residential electoral/telephone and business
searches, JSON Lines/CSV exports and streaming catalogue imports through the
ordinary `Database` API. The explicit decoder family is `v14`; it does not change
how the earlier SE sources are decoded. No original installer or decoder code is
executed by the reader.

The source images are `UK-Info V14 INST.mdf` (637,314,768 bytes) and `IMAGE.img`
(481,052,208 bytes). Their ISO metadata records 27 March 2008. Neither the mastering
date nor the supplied folders' later filesystem timestamps establish the records'
electoral-roll reference date. No public archive copy has been independently verified.
See [media/file fingerprints](../validation/v14-2008-media-inventory.json).

## Prepare both discs

The installation MDF stores 2448-byte sectors; the CloneCD data IMG stores
2352-byte sectors. Both contain Mode 2 data with 2048-byte payloads starting at
byte 24. They cannot be treated as ordinary 2048-byte ISO images. The preparer
checks both complete image SHA-256 fingerprints before extraction and refuses
mixed releases, changed images and an existing output directory.

From a source checkout on macOS or Linux, build the existing cabinet helper if
necessary. This requires CMake and a C compiler, and downloads pinned open-source
unshield code; it does not install or run the original Windows software:

```sh
python tools/build_cabinet_runtime.py build/desktop
mkdir -p private
python -m ukinfo_reader.v14_media \
  --installation 'UK-Info_v14_Instal/UK-Info V14 INST.mdf' \
  --data 'UK-Info_v14_data/IMAGE.img' \
  --output private/v14-reader
ukinfo-read --data private/v14-reader --identify
ukinfo-read --data private/v14-reader --surname Example --limit 20
ukinfo-read --data private/v14-reader --entry-type business --limit 20
ukinfo-validate --data private/v14-reader --output private/v14-validation.json
```

Install the Python project first as described in the [quick start](../reader-quick-start.md).
Extraction retains at least 5 GiB free, streams selected files and removes temporary
cabinets. It verifies all fifteen required files against the edition profile.
MDS/CCD/SUB sidecars are retained with the original media but are not required for
this exact extraction. Copy-protection metadata is not executed or emulated.

The desktop wizard can import the resulting **prepared folder** when built from
this revision. Its ISO/7z picker does not select both raw v14 discs automatically.
A future desktop download must include this revision before it can import v14.
Use the existing [streaming import procedure](../search-app.md) for self-hosting;
no full intermediate JSONL file is needed. The hosted archive has not imported v14.

## Required files and source transformations

The data disc supplies `uk.dat`, `d5.dat` and `lobdesc.dat`. The installation
cabinets supply `d1.dat`, `d2.dat`, `d3.dat`, `d4.dat`, `d6new.dat`, `d7.dat`,
`d8.dat`, `ukspos.idx`, `bus.dat`, `dd.dat` and `dbsic.dat`.

The fifteenth file, `telephone-prefixes.dat`, is generated from the user's
`ICD_14.DLL`: a NUL-separated sequence of 3,078 source telephone prefixes.
The preparer verifies the exact DLL fingerprint and reads its bounded PE32 data
sections. It copies no executable code, uses no Windows runtime, and requires
neither an emulator nor the DLL after preparation. The generated file has its own
fingerprint in the [edition registry](../../src/ukinfo_reader/editions.py).
Original binaries and the extracted prefix dictionary are not distributed in Git.

Optional original search/classification/map indexes are not needed by this reader.
In particular, `mlob.idx` has a comparison order that is not assumed to be bytewise;
its ordering check is not disabled globally. Business classifications resolve
through each record's industry and SIC references instead.

## Physical record differences

Residential records retain the earlier flag byte and one-to-five stored names,
but use a different layout:

| Field | v14 representation |
| --- | --- |
| First name code | Four bytes at offset 1, masked to 27 bits; low 22 bits select the name dictionary |
| Postcode | Three bytes at offset 5; low 22 bits select `d6new.dat` |
| House | Two bytes at offset 8 |
| Additional names | Four bytes each, starting at offset 10 |
| Building (`flags & 0x80`) | Four bytes |
| Subbuilding (`flags & 0x40`) | Two bytes |
| Associated telephone name (kinds 2/5) | Three bytes |
| Telephone code (kinds 1–6) | Four bytes |
| Precision (`postcode byte & 0x80`) | One byte after the optional fields |

`postcode_flags` preserves the high control bits, including the original field
labelled `CO1` (`0x40`), exposed as `source_co1`. A
[complete control-bit audit](../validation/v14-2008-03-source-controls.json) finds
29,410 physical records with this bit. Its broader meaning and original Windows
UI filtering are not inferred; the reader preserves it without inventing an
exclusion rule from the field name.

Only kinds 0, 3, 4 and 5 occur in the supplied residential stream. The complete
surname index supplies each record range's surname; it is not stored in every
physical record. Electoral names and telephone occurrences remain separate rows.
No update/deletion stream is present in this exact source.

Business records retain three-byte word references, but industry and building
references are four bytes. Telephone and fax codes are four bytes, replacing
separate stored subscriber/area fields. The postcode control bits retain the house
extension and telephone/fax prefix-extension controls. Source kinds 1 and 2 are
preserved. Industry offsets are full-width string offsets: the older SE reader's
24-bit wrap recovery is not applied.

Address records still join postcode → street/locality → post town/county, with
premises and subbuilding dictionaries kept separate. Fixed-table resource bounds,
all postcode/locality joins, all residential dictionary references, surname record
boundaries and every business join are checked by complete validation.

## Telephone numbers and uncertain source values

A telephone code's high twelve bits select a prefix (one-based); its low twenty
bits provide the suffix. The original formatter appends the final six decimal
suffix digits, including leading zeroes. Business extension bits extend the prefix
index. Unknown indexes produce an empty display plus a source warning.

Prefixes can contain subscriber digits, so `phone_prefix`/`fax_prefix` are not
labelled as telephone area codes. `phone_area_code`/`fax_area_code` remain zero.
`phone_code_raw`/`fax_code_raw`, source prefixes and suffixes preserve the original
representation. Four prefix-table entries contain punctuation. Affected displays
are empty with `invalid_phone_prefix`; the reader does not invent corrected digits.
A numeric source value is not a guarantee that a telephone number is valid today.

Partial postcode controls retain the earlier source precision rules: shortened
postcodes suppress street text, and broader controls also suppress locality text.
Raw postcode values are preserved separately. Unterminated locality text is flagged.

### Stale original locality overrides

The original v14 DLL carries county/name overrides from older releases even though
its locality dictionary changed. Applying those IDs to v14 can replace a stored
county with an unrelated one. This reader follows the v14 dictionary's stored town
and county parents and adds `legacy_locality_override_ignored` where that differs.
`county_source_id` and `town_source_id` retain the selected place row's original parent references. `resolved_county_source_id` records the county reached through its town parent.

The original formatter's separately verified Orkney/Shetland locality roles are
retained. An [all-locality comparison](../validation/v14-2008-03-locality-comparison.json)
checks all **27,957** dictionary rows: **50** intentional, flagged differences and
zero unaccounted differences. Parent types and bounds are checked independently.
This prevents an old display workaround becoming a silently wrong v14 county;
it does not claim independent historical-geography verification.

## Verification and limits

The [complete report](../validation/v14-2008-03.json) covers **43,799,502 source
occurrences**, including **6,092,008 business entries**. These are not counts of
unique people, households or companies. All 23,601,871 residential physical records,
6,092,008 business physical records and 957,370 surname-index boundaries were scanned.

[Original-routine comparisons](../validation/v14-2008-03-reference-comparison.json)
cover 640 residential field/length cases, 3,072 business field/length cases and
6,156 telephone-formatter cases with invented input and zero mismatches. The local
x86 emulator stubs allocation, arrays and CString runtime operations; it does not
replace the field readers or formatter logic. Emulator dependencies, original
binaries and recovered code are not part of the project distribution.

This is not a comparison with the running Windows UI, independent confirmation of
historical addresses, or performance qualification of a six-edition hosted index.

Complete [compatibility rescans](../validation/v14-2008-03-existing-source-regressions.json)
retain the original 2003, 2004 and 2005 entry totals after the shared reader hooks
changed. Invented tests cover the two older formats as well as v14; source and
wheel packages were checked to exclude original media, dictionaries and binaries.
